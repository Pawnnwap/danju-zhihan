**免费层使用条款（2026-10-13 逐字核验 https://open-meteo.com/en/terms）**：非商业用途 + 接受 CC BY 4.0 署名，调用量上限为**每日 10,000 次、每小时 5,000 次、每分钟 600 次**；**商业用途需付费订阅（API Key）**。含义：赛事期与公益免费阶段属非商业用途，零账单成立；一旦走收费服务线，同一数据链路即为商业使用，须改付费 Key 或换数据源，该项成本必须计入定价——"边际成本≈0"的说法不适用于收费阶段（`docs/03` §8 据此把 12 个月内收入定为 0）。

**数据链路**：浏览器直接调用 Open-Meteo API（CORS 开放、免密钥），无自建后端、无数据落库；用户输入的自定义坐标仅保存在本机。
**失败模式与可观测性**（唯一外部依赖，故显式处理）：每请求 12 秒超时 + 一次重试；返回前做契约校验（`daily.time` 与四个变量数组必须存在且等长，缺失或长度不齐即显式报错，不让 `undefined` 静默变成等级）；历史序列与预报序列**分别降级**——archive 挂了仅显示预报并提示"干旱暂不判级"，预报挂了仅显示再分析，两者都挂才报错并分别给出原因；两条取数路径的缺测处理规则已统一（同日剔除缺测行，避免评审 A-Q4 指出的"null 当 0mm 又当有水"的双重虚高）。

**已知局限（诚实声明）**：
1. ERA5-Land 为格点再分析，与具体果园实测存在偏差——"园块"实为用户坐标映射到最近格点的乡镇尺度背景场（请求坐标 32.60,111.42 → 实际格点 32.5835,111.3764，海拔 236 m）。**我们尚无同站偏差统计**：竹山站 44.6℃ 与格点 40.9℃ 是不同站、不同日的叙事性对照，不构成该格点的系统偏差估计；格点 vs 丹江口站逐日偏差统计列入试点前补做（Mean Bias + 极端日分位，脚本随材料开源）。正式版将接入省气象局授权的乡镇级实况/预报数据（需签约主体与授权资格，本项目当前两者皆无，故列为远期观察项）；
2. 物候表为库区常规年景近似日历区间，未建模年际波动与品种差异（暖冬年花期可提前 7–10 天）；区间已无缝覆盖全年，且由脚本对 2016–2028 每一天核算"显式命中、不靠兜底分支"（此前闰年 2/29 会静默落入兜底，已修）；中期计划改积温模型；阈值属文献推定，待 2027 花期试点校准；
3. 干旱为**双口径取高者**：①降水型（连续无有效降水日 <1mm 达 8/15/25 天，或近 30 天累计降水 ≤45/30/15 mm）；②蒸散型（def30 = 近 30 天 ET0 累计 − 近 30 天累计降水，按物候期自身十年 p75/p90/p99 判级，见 §5）。工程约束：30 天回看窗口不满或窗口内含缺测日一律不判级；ET0 缺测时蒸散口径整体退出该日（定标与运行时同一套缺测语义，见 §5）。降水口径在**休眠期沉默**：十年基线核算显示照判则 89.8% 的越冬天数会带等级、其中 37.5% 为"重"级，属纯噪声；休眠期仍可凭蒸散口径出级（其阈值取自该期自身分位，样本内常驻率约 25%/10%/1%）。暴雨后 30 天窗口内雨量计入累计、干旱自然退出（保守取舍，未做土壤水分订正）；
4. 阈值为文献通用值，试点期将用合作社地块反馈校准；
5. **预报路径零回测**：实时运行中当日等级依赖 ECMWF 预报（archive 滞后 2–5 天，代码取至 now−6d 并用预报 past_days=6 回填），"提前 3 天"是描述性回测指标而非预报技巧。预报回测**验收口径**（承诺条款）：①序列选用 Open-Meteo 历史预报存档的 ECMWF 单模型，与线上 best_match 混合序列的差异单独声明；②判定规则=逐日等级差 ≤1 档记可用、≥2 档记误报，按预报时效（lead 1–3/4–7/8–16 天）分箱统计；③90 天试点极端过程期望 ≤2 次，只作记录与积累，技巧评估依托历史存档年度样本。8 天外预报等级已封顶"关注"并以"模式值"口径展示。

## 2. 可复算性与等价性闸门

评审复算不必当场联网，也不需要区分"差异来自引擎还是数据"——输入序列已冻结进仓库。四条命令：

```bash
python tools/backtest.py --fixture tools/fixtures/liangshuihe_2016_2025.json \
       --start 2022-06-01 --end 2022-09-30 --check   # 头条数字回归闸门（离线）
python tools/parity_check.py                         # JS↔Python 逐日对拍 + 边界用例 + 阈值单一事实源
python tools/baseline_stats.py                       # 十年基线、常驻率、def30 定标与留出检验
python tools/mutation_test.py                        # 闸门自证：注入回归，看闸门是否拦下
```
（`tools/backtest.py` 不带 `--fixture` 即联网复算；`parity_check.py --online` 改为联网取真实窗口，可用来发现冻结序列与线上的漂移。）

**`parity_check.py` 的三层检查（当前全绿）**：
1. 真实序列逐日对拍：4 个窗口（热害季/越冬期/春夏物候边界密集/秋汛至采收）共 **442 天**，比较物候判定与四类风险等级；窗口缺失或天数不足 400 直接判失败，不允许"跳过某些窗口还宣布通过"；
2. **33 组边界合成用例**：rain30 的 14.97/15.03/29.97/30.04/44.97/45.03、连旱 7/8/15/25 天、连续高温 1–6 天升级链、单日 33/35/37/39℃ 台阶、断链清零、窗口不满 30 天、窗口含降水缺测日、ET0 缺测退出、def30 的 p75/p90/p99 六个边界、闰日、以及开花期封顶。期望值按规则文本单独写死（不取自任何一侧实现）；
3. **常量绑定**：物候表 JS==Python 且 2016–2028 每天显式命中；`DEF_THRESH`/`DEF_MAX_LEVEL` JS==Python==用冻结序列现算的 p75/p90/p99（±0.05）——这一层就是为消灭"三处手抄阈值"而加的（评审 A-Q9）。

**闸门自证（`mutation_test.py`）**：把修过的每类分叉重新注入一份临时副本，逐个跑三道闸门，**要求每个变异都真的执行并被拦下**；注入点失效会记为"未执行"并使整轮失败（此前版本会把没打进去的变异算成拦下来的，评审 A-Q2 指出后已修）。当前：**执行 15/15、拦下 15/15**——单侧改阈值、去掉休眠期沉默、恢复取整口径、去掉窗口闸门、物候表退回闰日洞、幼果期阈值收窄、拆掉外部性 confirm 标记、取消开花期封顶等均由对拍或烟测拦下；"两侧同步改 39℃"这类实现仍等价的改动由回归闸门（头条数字）拦下，证明三道闸门互补而非重复。

## 3. 回测结果（2022-06-01~09-30，凉水河格点，带 35 天 warm-up）

```
≥35℃ 日数: 30
热害『重』级日数: 13
极端最高温: 40.9℃（2022-08-07）
首个『重』级提示: 2022-08-04（39.2℃，当日连续 3 天 ≥35℃）
首个『重』级触发方式: 单日 ≥39℃
提示相对峰值提前: 3 天
『重』级中由连续日数升级产生（当日 <39℃）: 3 天，最早 2022-08-10
干旱：首个『轻』级以上提示 2022-06-01；『重』8 天、『中』54 天；最长连旱 12 天
回看窗口不满 30 天或有缺测的日数（不判干旱）: 0
```

**warm-up 说明（这是本轮更正的核心之一）**：回测必须像产品那样喂数据。此前从 `--start` 直接切片，会让窗口前 29 天撞上"回看不满 30 天不判级"，于是干旱数字是人为致盲的伪影（当时"重 20/中 15/首个 06-30"）；改为先取 `start−35 天`再只报告区间内的日之后，2022 年干旱实为**"重"8 天／"中"54 天，首个提示 06-01**。`--check` 断言的正是这组数，并把"窗口不满天数"也纳入断言（值必须为 0），防止同类伪影再次混进材料。
**时效归因（不抢功）**：把"提前 3 天"记在连续日数升级机制上是错的——首个"重"级由**单日 ≥39℃ 阈值**触发（08-04 达 39.2℃，早于 08-07 峰值）；升级机制在同过程另贡献 3 天"重"级，但最早出现在 08-10（峰值之后）。因此该时效的证据支持的是分级阈值链，升级机制的价值在长过程的中重级持续覆盖（13 天）。

## 5. 蒸散亏缺（def30）口径：定标、留出检验与封顶

**可行性**：`et0_fao_evapotranspiration`（FAO 参考蒸散，mm/日）在 Archive 与 Forecast 两端点均有日值，已实测可取（早前材料写的 `et0_reference_evapotranspiration` 在两端点均返回 invalid，已更正；土壤水分变量仅有小时值，需自行日聚合，首发版未用）。

**定标**：def30 = 近 30 天 ET0 累计 − 近 30 天累计降水，按物候期取自身十年 **p75/p90/p99** 作为轻/中/重线（唯一生成处 `tools/baseline_stats.py:derive_thresholds()`，代码常量由 `parity_check.py` 第 3 层绑死）：

| 物候期 | 轻 | 中 | 重 |
|---|---|---|---|
| 休眠 | 34.0 | 40.7 | 48.4 |
| 萌芽/现蕾 | 43.0 | 56.8 | 84.0 |
| 开花 | 55.3 | 86.0 | 102.3 |
| 幼果 | 83.5 | 102.3 | 116.7 |
| 膨大 | 54.1 | 87.4 | 122.6 |
| 成熟采收 | 31.4 | 55.5 | 97.5 |

**两条必须写在前面的自我批评**：
1. **上一轮我打了稻草人**。我用"把单一全局 def30 阈值 OR 并入会让膨大期'重'级从 0 天/年升到 38 天/年"作为不上线的理由，而评审指出正路是按物候期分位定标——按正路重算，膨大期"重"级基线与现行口径同量级，所以我上轮的否定结论不成立，本节即为更正后的结论：蒸散口径**已上线**（只抬高等级、不压低）。
2. **分位占比不是证据**。按定义，定标样本自身的占比必然≈25%/10%/1%，那是分位数的算术。真正的检验是**留出**：用 2016–2020 定标、判 2021–2025，结果六档里五档可用（轻/中/重占比 8–22%/0.3–14%/0.3–6%），但**开花期严重失准——留出段"重"级占比 19.4%（单年最高 30 天）**。处置：给开花期的蒸散口径**封顶"中"**（`DEF_MAX_LEVEL`），2027 年春季花期田间对表完成前不允许一个相对分位单独决定最高级的响应强度；这条封顶本身也纳入常量绑定与变异测试。

**def30 到底测了什么（评审 A-Q6b）**：各物候期 30 天累计的中位数显示，膨大期 ET0 中位 123.8 mm 远高于休眠期 41.6 mm，但 def30 中位反而更低（13.7 vs 20.6）——因为夏季降水大得多。所以 def30 是"降水亏缺扣掉蒸散需求"的**合成排名量**，不等于作物缺水强度；它的增量信息集中在"高 ET0 + 少雨"的过程，这正是相对纯降水口径的实际增益点。

**可达性分解（评审 A-Q6a）**：现行降水口径在膨大期十年内 `连旱≥25` 命中 **0 次**、`雨30≤15` 仅 6 次（膨大期雨30 中位 110.2 mm），即旧版"重级 0 天/年"更多是**结构不可达**而非信号稀有——因此不能据旧的 0 天/年宣称"高级别稀有"。蒸散口径的 `p99` 线补的正是这一段：2022-08-24~27 该格点 def30 = 127.6/130.8/138.3/123.2 mm，全部超膨大期 p99（122.6），引擎判"重"；而纯降水口径同一周最高只判到"中"。同一周正是中国气象局首次在丹江口汇水流域实施飞机人工增雨的时段（公开报道，2022-08-27）——这就是新分支可核验的作用点。

**仍未证明的**：def30 的绝对农学含义（需田间水分观测，见 docs/03 §3 记录项⑤与 §6）、与本地灾情的逐次对表（docs/03 §6）、以及"用户据此少损失多少"。本节只把分级从"说不清"提升到"可复算、可判失败"。

## 7. 模型与工具使用

### 7.1 确定性风险引擎（核心）
- 实现：`phenology.js`（物候表、四类风险判级、蒸散阈值与封顶）+ `app.js assess()`（前端逐日计算，含 30 天回看窗口与 ET0 完整性判定）；`tools/backtest.py` 提供同规则 Python 独立实现（四类风险全覆盖）用于回测与基线核算。
- 输入：逐日 tmax/tmin/precipitation/ET0（含前 30 天回看窗口）。
- 输出：逐日四类风险等级（无/关注/轻/中/重）与触发依据文本；**"无"三态已区分**：今日未触发／该期不判级（休眠期降水口径沉默、回看不满 30 天、ET0 缺测）——页面与导出、问答都分开表述，不再把"不判级"写成"没有旱情"。
- 特点：全部阈值显式写在代码中、可审计、可回测，两侧等价性被脚本强制。

### 7.2 DeepSeek 大模型解释层（可选接入）
- 接入方式：用户在本机填入自己的 DeepSeek API Key（仅存 localStorage，不经任何服务器），前端直连 `api.deepseek.com/chat/completions`。
- 系统提示词约束：只用给定数据上下文与公开农技规则回答；给出可执行动作；必须引用数据日期；**风险等级与数值只能原样引用上下文，不得自行判定等级或预测新数值**；数据不足时明说并建议咨询当地农技部门。
- 上下文含当日与**未来 7 天**逐日数据及引擎等级（早前只给历史 7 天，问"接下来几天"时模型无据可依）。
- 技术侧约束（不只靠提示词）：①等级一律由规则引擎计算并渲染看板，LLM 文本不参与计算；②LLM 返回文本与用户提问回显一律 HTML 转义后渲染（杜绝注入）；③回答尾部固定"风险等级请以页面看板为准，本回答仅为解释；不构成灾害预警"。
- **仍存在的缺口（不捂）**：没有对 LLM 文本做"等级词/数值与引擎一致性"的自动后校验；规模化前需加轻量后校验（抽取文本中的等级词与引擎结果比对，不符则拒渲并回退规则答案）。
- 建议来源的措辞：页面与导出报告在每条规则来源后固定标注"（本项目按公开技术文件自行整理的规则摘录，与发文单位无关联，未经当地核验）"，避免把省厅文件名读成官方背书（评审 C-Q8）。

### 7.3 建议库的外部性分级（fail-closed 的产品实现）
- 数据层：`ADVICE` 中含环境外部性的动作（熏烟与明火、地膜/覆盖材料残膜、大水漫灌与退水、化学品与叶面肥/速效肥）标 `confirm: true`，共 15/35 条。
- 行为层：这类动作**默认不进入"可执行建议"列表**，而是单列"待当地确认清单（未确认前不作为可执行建议）"；现场经农技员/主管部门确认后，把该动作文本写入本机 `localStorage.confirmed_actions` 才升格，并标注"已经当地确认"。看板、导出报告、规则问答三处同规则。
- 机制保障：`tools/smoke_app.mjs` 用关键词（熏烟/覆膜/地膜/磷酸二氢钾/保水剂/叶面肥/速效肥/喷药/灌透水/冻前灌水/追施）做**语义断言**——凡命中关键词必须挂 confirm，且未确认项必须落在待确认区；拆掉任意一个标记都会被拦（`mutation_test.py` M12/M13 实测）。
- 诚实边界：本工具无推送通道，所谓"不推送"在产品上等于"不作为可执行建议呈现"；确认状态保存在用户本机，不构成合规凭证。库区焚烧/覆膜/退水的**答复权限归属**（乡镇政府、生态环境部门还是农技员）属待核事项，见 docs/03 §3。

### 7.4 为什么不是"为了 AI 而 AI"
- 没有大模型时产品依然完整可用（规则引擎 + 规则问答 + 导出报告/CSV）；
- 大模型解决"同一份数据对不同用户的不同表述 + 支持追问"这一具体负担，任务边界明确；
- 评审可复算：回测与基线脚本独立于前端，且已证明两套实现逐日等价、阈值与定标同源。

## 8. 材料一致性（数字不再靠人记）

`tools/docs_consistency.py` 把 README、docs/01–03 与 PPT 生成脚本里出现的**关键数字与口径**（2022 头条三项、442/33/15 三个测试计数、十年基线三档、89.8% 常驻率、休眠期与开花期表述、已被否决的旧措辞）逐条与"从冻结序列现算出来的值"比对，不一致即非零退出。提交前必须跑绿——上一轮"改了一处、三处载体没跟上"被评审当面抓到，这一轮改成机器拦。
