**免费层使用条款（2026-10-13 逐字核验 https://open-meteo.com/en/terms）**：非商业用途 + 接受 CC BY 4.0 署名，调用量上限为**每日 10,000 次、每小时 5,000 次、每分钟 600 次**；**商业用途需付费订阅（API Key）**。含义：本项目为**全公益产品、永久非商业用途**，零账单成立且与数据许可**永久自洽**（不存在"商业化后换付费 Key"的分支）；任何第三方将本仓库代码用于商业部署时，须自行取得数据授权并改用付费数据源（README 许可边界已写明）（`docs/03` §8）。

**已知局限（诚实声明）**：
1. ERA5-Land 为格点再分析，与具体果园实测存在偏差——"园块"实为用户坐标映射到最近格点的乡镇尺度背景场（请求坐标 32.60,111.42 → 实际格点 32.5835,111.3764，海拔 236 m）。**偏差量级已实测（`tools/grid_sensitivity.py`，联网，2026-10-14 重测）**：对凉水河周边 4 个相邻请求点（含 Open-Meteo 依海拔做的高程订正差异）跑同一区间，**46.7% 的日子里四类风险的最高等级在不同格点间不一致**；分风险看**干旱 59/122 天（48.4%）最依赖格点选择**，热害 18/122 天，低温与冻害 0 天（温度类阈值本身平滑）；**2022 年干旱"重"级日数在 0–7 天之间摆动**（热害"重"级 13–16 天；两类的合并高级别日数在格点间极差 10 天，13–23 天）。该次重测同时修掉了本脚本的两处旧缺陷：把"关注"与"无"同记为 0 档（会低估分歧）与按下标而非按日期对齐（某格点缺测日会造成假分歧）——**修复前算法给出的分歧率已作废，材料不再引用旧值**。也就是说，格点选择本身足以改变结论，"乡镇尺度背景场"不是谦辞而是测量结果；页面因此对所有触发的风险都保留"结合园地位置判断"的提示。**我们尚无与地面气象站的同站偏差统计**：竹山站 44.6℃ 与格点 40.9℃ 是不同站、不同日的叙事性对照，不构成该格点的系统偏差估计；格点 vs 丹江口站逐日偏差统计列入试点前补做（Mean Bias + 极端日分位，脚本随材料开源）。正式版将接入省气象局授权的乡镇级实况/预报数据（需签约主体与授权资格，本项目当前两者皆无，故列为远期观察项）；
2. 物候表为库区常规年景近似日历区间，未建模年际波动与品种差异（暖冬年花期可提前 7–10 天）；区间已无缝覆盖全年，且由脚本对 2016–2028 每一天核算"显式命中、不靠兜底分支"（此前闰年 2/29 会静默落入兜底，已修）；中期计划改积温模型；阈值属文献推定，待 2027 花期试点校准；
3. 干旱为**双口径取高者**：①降水型（连续无有效降水日 <1mm 达 8/15/25 天 → 轻/中/重；其中"轻"还需 30 天累计降水 ≤45mm 同时成立；"中"为连旱 ≥15 天或累计 ≤30mm，"重"为 ≥25 天或 ≤15mm）；②蒸散型（def30 = 近 30 天 ET0 累计 − 近 30 天累计降水，按物候期自身 2016–2020 定标段 p75/p90/p99 判级，见 §5）。工程约束：30 天回看窗口不满或含缺测日一律不判级；ET0 缺测时蒸散口径整体退出该日（定标与运行时同语义）。**降水口径在休眠期沉默**，但蒸散口径仍可出级。噪声治理不是一次性的：本轮实测发现噪声并不只在休眠期——**萌芽·现蕾期"30 天累计 ≤45mm"十年命中 258/400 天（64.5%）**，若单凭它报"轻"则该期六成天数带级，因此"轻"改为双条件（连旱≥8 天 且 累计≤45mm）；改后干旱"轻"级年日数中位由 69 降到 43（§4）。各级常驻率与命中次数的唯一生成处是 `tools/baseline_stats.py`，代码注释与文档都不复制数字（评审 C-Q2 指出的"第二套事实"）；
4. 阈值为文献通用值，试点期将用合作社地块反馈校准；
5. **预报路径零回测**：实时运行中当日等级依赖 ECMWF 预报（archive 滞后 2–5 天，代码取至 now−6d 并用预报 past_days=6 回填），"提前 3 天"是描述性回测指标而非预报技巧。预报回测**验收口径**（承诺条款）：①序列选用 Open-Meteo 历史预报存档的 ECMWF 单模型，与线上 best_match 混合序列的差异单独声明；②判定规则=逐日等级差 ≤1 档记可用、≥2 档记误报，按预报时效（lead 1–3/4–7/8–16 天）分箱统计；③90 天试点极端过程期望 ≤2 次，只作记录与积累，技巧评估依托历史存档年度样本。8 天外预报等级已封顶"关注"并以"模式值"口径展示。

## 2. 可复算性与等价性闸门

评审复算不必当场联网，也不需要区分"差异来自引擎还是数据"——输入序列已冻结进仓库。四条命令：

```bash
python tools/backtest.py --fixture tools/fixtures/liangshuihe_2016_2025.json \
       --start 2022-06-01 --end 2022-09-30 --check   # 头条数字回归闸门（离线）
python tools/parity_check.py                         # JS↔Python 逐日对拍 + 边界用例 + 阈值单一事实源
python tools/baseline_stats.py                       # 十年基线、常驻率、def30 定标与留出检验
python tools/mutation_test.py                        # 闸门自证：注入回归，看闸门是否拦下
```
（`tools/backtest.py` 不带 `--fixture` 即联网复算；`parity_check.py --online` 改为联网取真实窗口，可用来发现冻结序列与线上的漂移。）

**`parity_check.py` 的三层检查（当前全绿）**：
1. 真实序列逐日对拍：4 个窗口（热害季/越冬期/春夏物候边界密集/秋汛至采收）共 **442 天**，比较物候判定、四类风险等级与四类归因文案；窗口缺失或天数不足 400 直接判失败，不允许"跳过某些窗口还宣布通过"；
2. **37 组边界合成用例**：rain30 的 14.97/15.03/29.97/30.04/44.97/45.03、连旱 7/8/15/25 天、连续高温 1–6 天升级链、单日 33/35/37/39℃ 台阶、断链清零、窗口不满 30 天、窗口含降水缺测日、ET0 缺测退出、def30 的 p75/p90/p99 六个边界、def30 超 p99 时「雨30=30.0（佐证成立→重）vs 31.0（无佐证→封顶中）」这一对、闰日、休眠期与开花期无佐证封顶。期望值按规则文本单独写死（不取自任何一侧实现）；
3. **常量绑定**：物候表 JS==Python 且 2016–2028 每天显式命中；`DEF_THRESH`/`DEF_SOLO_CAP` JS==Python==用冻结序列 2016–2020 定标段现算的 p75/p90/p99（±0.05）——这一层就是为消灭"三处手抄阈值"而加的（评审 A-Q9）。

4. **四类风险的归因文案全部对拍**：干旱、热害、低温、冻害的"为什么是这个等级"说明串（含"分位达重级线、降水未佐证故按中处理"这类降格说明、热害的连续日数升级句、冻害的微地形声明）逐字符比对，两套实现不许各写一套（评审 A-Q4/A-Q8：此前只比对干旱，热害的 JS 写"最高温 39.2℃ ≥39℃"而 Python 写"39.2℃"，两轮都没被抓到）；对拍同时绑定物候期**中文名**，因为低温文案里用的是期名；真实窗口的等级在带 35 天 warm-up 的序列上算，比对只取报告区间（评审 A-Q5：不这么做，窗口头 30 天两侧都被回看闸门沉默，那种一致没有信息量）。
   本轮再加 **5 组"限定词用例"**（对拍第 4b 层）：删掉"本地未联校""相关性而非因果""乡镇尺度背景场""超休眠期自身 p90 门槛"这类**诚实声明不会改变任何等级**，所以它们必须被断言——每组用例同时钉**四件事**：①两侧文案逐字相同；②该风险确实出了预期等级（防"空用例蹭过"）；③必含子串确实在文案里，且休眠期那条的 needle **带门槛数字本身**（由 `backtest.DEF_THRESH` 现算拼接，只钉短语时把门槛改回 p75 照样全绿）；④**禁含断言**——被限定的因果断言不许混进文案（热害句不得出现"减产／绝收"，休眠句不得退回"超该物候期定标分位"那种无门槛表述）。另有条数下限 `MIN_WORDING_CASES`，**取值等于清单实数（5）**：下限低于实数就等于允许先悄悄删一条再"0/0 全过"。当前 5/5 通过，实跑数印进对拍汇总行。
5. **1302 个逐日比对点位**（评审 A-Q2/A-Q3：只给人工写死的边界点测不出"倒挂"；上一版的扫描只比每档末日、共 27 个点位，且 71 天步长让各档落进不同物候期，方向断言实际由 27 个跨期点位撑着——本轮改成**5 条轴、每档 31 天、每条轴整段落在同一个物候期内、逐日全比**，同一日位上的各档可直接比较）：
   - 旱情递增（逐日雨量 10→0.2 mm，并从第 3 档起在末尾叠加 8/8/15/15/25/30 天旱日）→干旱：末日等级序 无→无→轻→中→中→重→重→重，**旱情加重等级不得减轻**；
   - 逐日最高温 25→41℃（10 档，膨大期）→热害：无→无→关注→关注→重→…→重（35℃ 一档直接到"重"是连续日数升级的设计结果，非倒挂）；
   - 逐日 ET0 10→25 mm（8 档，def30 0→450 mm，膨大期）→干旱：无→轻→中→中→…→中，**超 p99 的档全部被佐证规则压在"中"**——这一条正是全局封顶规则生效的可复算证据；
   - 花期最低温 0→9℃（8 档，起点 2023-04-10 开花期）→低温：重→重→中→中→关注→关注→无→无；
   - 越冬期最低温 −8→0℃（8 档，起点 2023-01-05 休眠期）→冻害：重→重→重→中→中→轻→轻→无。
   两侧（JS/Python）等级与**该风险自己的**归因文案逐日相同（干旱比 why、热害比 heatWhy、低温比 coldWhy、冻害比 freezeWhy；上一版扫描只比 why，热害/低温/冻害那 26 档 × 31 天＝806 个点位的归因其实从没进过比对，本轮补齐并把字段名印进扫描输出行）。扫描另加两条自检：每档两侧天数不等即报错（zip 静默截断会让实跑点位数与材料印的设计值脱钩），实跑点位与设计值 42 档 × 31 天＝1302 不等即失败（8＋10＋8＋8＋8＝42 档 × 31 天 = 1302 个点位全部比对，不再只比每档末日）；比对点位低于 1200 即判失败，防止扫描被缩水或静默跳过。扫描与真实窗口**共用同一条 warm-up 准则**：每档先喂 35 天预热 30 天回看窗口，只比报告区间内的日（上一版没做，导致 1302 个点位里 626 个是"两侧都因回看不满而沉默"的一致——数量对得上但没有信息量，评审 A-R9①）。现在闸门自己数：每条轴出级点位不得少于一半、整体不得少于 70%，实测值随扫描一并打印。另保留"末日等级不得少于 3～4 个不同档"的信息量断言（评审 A-Q8：取值区间选错导致的"全 null 一致"零信息量扫描不算通过）。

**一键全绿与提交闸门（`tools/check_all.py` → `tools/GATES.json`）**：单说"闸门存在"不够，还得证明**同一份代码 + 同一份冻结输入上它们同时为绿**。`python tools/check_all.py` 按固定顺序跑六件事（对拍、头条回归、基线/留出与不变量、前端烟测、变异自证、材料一致性），全通过才写 `tools/GATES.json`，内容是：被验证的 commit 短号与工作树是否干净、冻结文件的实际格点与 `pulled_at_utc`、每道闸门**自己声明**的核查条数（对拍天数/用例组数/回归断言/材料检查项）。任一失败退出 1 且**不覆盖**上一次成功记录。强制方式：`.githooks/pre-commit` 跑 `check_all.py --verify`，需仓库所有者执行一次 `git config core.hooksPath .githooks`（本项目不自动改 git 配置，所以这里给的是命令而不是既成事实）。**自指说清楚**：GATES.json 里的 commit 是"被验证的那棵树"，把这条记录本身提交会产生一个不含代码/材料变更的记录性提交——评委核对时以"该 SHA 之后的记录性提交 diff 里没有代码/材料"为准，而不是要求 SHA 与 HEAD 恒等。**沙箱豁免写在明面**：变异测试把仓库副本放进临时目录跑 docs 闸门，那份副本没有 `.git`，因此"全绿记录核对"在沙箱内按跳过处理（`MUTATION_SANDBOX=1`，取不到记录时打印 `[未核]` 而不是"对得上"）；豁免只覆盖 git 记录这一项，材料数字与禁现检查在沙箱里照旧全跑，主树的严格模式（`check_all.py --verify`、pre-commit）不受该变量影响。页面与导出报告另印 `ruleStamp()` 口径串（规则版本号 + 定标段/留出段 + 蒸散单独出级上限），其常量由对拍第 3 层与 `baseline_stats.py` 的年份区间绑定（评审 C-Q：截图要能追溯到规则版本）。

## 3. 回测结果（2022-06-01~09-30，凉水河格点，带 35 天 warm-up）

```
≥35℃ 日数: 30
热害『重』级日数: 13
极端最高温: 40.9℃（2022-08-07）
首个『重』级提示: 2022-08-04（39.2℃，当日连续 3 天 ≥35℃）
首个『重』级触发方式: 单日 ≥39℃
提示相对峰值提前: 3 天
『重』级中由连续日数升级产生（当日 <39℃）: 3 天，最早 2022-08-10
干旱：首个『轻』级以上提示 2022-06-01；『重』1 天、『中』55 天；最长连旱 12 天
回看窗口不满 30 天或有缺测的日数（不判干旱）: 0
```

**warm-up 说明（这是本轮更正的核心之一）**：回测必须像产品那样喂数据。此前从 `--start` 直接切片，会让窗口前 29 天撞上"回看不满 30 天不判级"，于是干旱数字是人为致盲的伪影（当时"重 20/中 15/首个 06-30"）；改为先取 `start−35 天`再只报告区间内的日之后，2022 年干旱实为**"重"8 天／"中"54 天，首个提示 06-01**（该组数是蒸散口径还能单独宣布"重"时的值；佐证规则上线后同一区间为 **"重"1 天／"中"55 天**，首日不变，`--check` 现在断言的是后者）。`--check` 断言的正是这组数，并把"窗口不满天数"也纳入断言（值必须为 0），防止同类伪影再次混进材料。
**时效归因（不抢功）**：把"提前 3 天"记在连续日数升级机制上是错的——首个"重"级由**单日 ≥39℃ 阈值**触发（08-04 达 39.2℃，早于 08-07 峰值）；升级机制在同过程另贡献 3 天"重"级，但最早出现在 08-10（峰值之后）。因此该时效的证据支持的是分级阈值链，升级机制的价值在长过程的中重级持续覆盖（13 天）。

**阈值贴边敏感性（`tools/threshold_sensitivity.py`，离线读冻结件即可复算）**：头条那两个数都贴着线，所以必须给出"偏移多少就翻"的量化答案。
- 热害：逐日最高温系统性偏冷 1.0℃ → "重"级 11 天、提前 2 天；偏冷 2.0℃ → 重级 5 天、提前 1 天；偏冷 4.0℃ → 重级 2 天、提前 −1 天（提示反而晚于峰值）。也就是说**"提前 3 天"这件事只在 ≤1℃ 的格点偏差下成立**。
- 干旱：逐日降水整体上移 0.5mm（再分析一次修订就是这个量级）→ "重"级 0 天、"中"级 25 天、首个提示推迟到 06-08；上移 2.0mm → 整个夏季 0 个干旱等级。
- 结论写死在材料里：**分级阈值对这些数字没有安全余量**，因此①对外只把等级讲成"相对排名的提示"，不宣称绝对受灾程度；②与田间墒情/灌水记录对表（docs/03 §3 记录项⑤）是解除该限制的唯一路径，未对表前"重"级动作建议一律要求现场核实。

## 5. 蒸散亏缺（def30）口径：定标、留出检验与封顶

**可行性**：`et0_fao_evapotranspiration`（FAO 参考蒸散，mm/日）在 Archive 与 Forecast 两端点均有日值，已实测可取（早前材料写的 `et0_reference_evapotranspiration` 在两端点均返回 invalid，已更正；土壤水分变量仅有小时值，需自行日聚合，首发版未用）。

**定标**：def30 = 近 30 天 ET0 累计 − 近 30 天累计降水，按物候期取自身 **2016–2020 定标段**的 **p75/p90/p99** 作为轻/中/重线（唯一生成处 `tools/baseline_stats.py:derive_thresholds(…, CALIB_YEARS)`，代码常量由 `parity_check.py` 第 3 层绑死）。此前用全段 2016–2025 定标，等于让同一份样本既当答案又当考卷——留出评估与头条回测（2022 年区间）都落在定标样本内；改为只用前五期定标后，2021–2025 的头条与负担数都是样本外结果：

| 物候期 | 轻 | 中 | 重 | 定标样本 n |
|---|---|---|---|---|
| 休眠 | 28.7 | 36.9 | 45.9 | 453 |
| 萌芽/现蕾 | 42.1 | 52.7 | 62.9 | 200 |
| 开花 | 54.4 | 66.9 | 82.0 | 155 |
| 幼果 | 77.2 | 99.7 | 126.3 | 205 |
| 膨大 | 54.2 | 88.7 | 120.9 | 460 |
| 成熟采收 | 38.4 | 61.9 | 98.4 | 325 |

**分位定义（评审 A-Q4）**：线性插值，与 `numpy.percentile(..., method="linear")` 同——此前用的是下标法 `v[int(q·n)]`，第三方按 numpy 默认口径复算会差到 0.8 mm，而材料承诺的"可独立复算"必须是别人也算得出同一个数的定义。样本 n 一并印出：n=155（开花期）时的 p99 只是定标段第 2 大的观测值，样本抖一档重级线就动，所以这张表的读数本身带着小样本误差，不能当绝对水分阈值用。上表每一格都由 `docs_consistency.py` 与现算分位逐格比对（改数不改表即提交失败）。

**两条必须写在前面的自我批评**：
1. **上一轮我打了稻草人**。我用"把单一全局 def30 阈值 OR 并入会让膨大期'重'级从 0 天/年升到 38 天/年"作为不上线的理由，而评审指出正路是按物候期分位定标——按正路重算，膨大期"重"级基线与现行口径同量级，所以我上轮的否定结论不成立，本节即为更正后的结论：蒸散口径**已上线**（只抬高等级、不压低）。
2. **分位占比不是证据**。按定义，定标样本自身的占比必然≈25%/10%/1%，那是分位数的算术。真正的检验是**留出**：用 2016–2020 定标、判 2021–2025，除开花期外五档的偏离还在同一量级（留出占比区间：轻 8.0–21.6%／中 4.0–20.8%／重 0.0–5.0%，对照恒等式的 25%/10%/1%），但**开花期严重失准——留出段"重"级占比 19.4%（单年最高 30 天）**。上一轮我只给开花期打了"封顶中"的补丁，评审 A-Q1 指出这是把个案当规则：**同一个论证（相对分位不足以宣布最高响应强度）是论证而非逐档实测**——留出实测支撑的是"除开花期外五档的重级占比区间 0.0–5.0%、开花期单点 19.4%"（由 `holdout_rate_ranges` 现算并被材料闸门绑定），因此封顶规则按论证全局生效，而不是"六档各自都被留出证明过"，所以现行规则改成全局的——蒸散口径**单独**最高只到"中"（`DEF_SOLO_CAP`），要出"重"必须降水口径自己也给出 ≥"中" 的绝对水量佐证（连旱 ≥15 天或 30 天累计 ≤30mm）。这条规则本身进常量绑定、进边界用例、进变异测试；`baseline_stats.py` 还断言其不变量"降水口径未达中却判重"的天数为 0（当前实算 0）。代价也写清楚：休眠期降水口径沉默，所以**冬季不再有"重"级干旱**，最不稳的开花期同理——只有当分位与绝对水量同时说话时，才给用户 24–48 小时内要行动的那一档。

3. **休眠期沉默的定量理由换了版本**。上一轮材料用"若降水口径照判则 89.8% 天数带级"给沉默决策做辩护，但那个数同时用了**已退役的 OR 规则**（连旱≥8 或 雨30≤45 即判轻）与**含回看不足日的分母**（963 天）。按现行 AND 规则、回看窗口完整的 934 天口径重算（`tools/baseline_stats.py` 第 2 节 DORMANT_AND_PCT），照判的常驻率是 76.0%（现行 AND 规则、回看窗口完整的 934 天口径；其中轻 4.2%、中 33.2%、重 38.7%）。结论不变——冬季仍有约四分之三的天数会挂着某个干旱等级、其中近四成是"重"，噪声依旧不可接受；但辩护数字必须是现行规则的产物，不是退役规则的（评审 A-Q9）。

**def30 到底测了什么（评审 A-Q6b）**：各物候期 30 天累计的中位数显示，膨大期 ET0 中位 123.8 mm 远高于休眠期 41.6 mm，但 def30 中位反而更低（13.7 vs 20.6）——因为夏季降水大得多。所以 def30 是"降水亏缺扣掉蒸散需求"的**合成排名量**，不等于作物缺水强度；它的增量信息集中在"高 ET0 + 少雨"的过程，这正是相对纯降水口径的实际增益点。

**可达性分解（评审 A-Q6a）**：现行降水口径在膨大期十年内 `连旱≥25` 命中 **0 次**、`雨30≤15` 仅 6 次（膨大期雨30 中位 110.2 mm），即旧版"重级 0 天/年"更多是**结构不可达**而非信号稀有——因此不能据旧的 0 天/年宣称"高级别稀有"。蒸散口径的 `p99` 线补的正是这一段：2022-08-24~28 该格点 def30 = 127.6/130.8/138.3/123.2/118.3 mm，其中四天超膨大期定标段 p99（120.9）。逐日实况可复算：**08-26 判"重"**（雨30=29.9 mm 使降水口径到"中"，佐证成立），**08-24/25/27 判"中"**（连旱仅 4–6 天、雨30 在 35–42 mm，降水口径未达"中"，按佐证规则降格），08-28 分位本身只到"中"线。纯降水口径这一周五天全部沉默或只到"中"——即蒸散口径的净增量在这里是**"无→中"四天（08-24/25/27/28）+ "中→重"一天（08-26）**，而不是整周"重"。同一周正是中国气象局首次在丹江口汇水流域实施飞机人工增雨的时段（公开报道，2022-08-27）。

- **两条数据链路的同重叠日核对（评审 A-R12⑥）——测到的不是有风险那一段**：新增 `tools/forecast_vs_archive.py`，同一格点同时取再分析与预报接口（`past_days=6`），2026-10-09~10-15 七个重叠日上 tmax／tmin 最大绝对偏差 0.2℃、降水与 ET0 偏差 0.0mm，替换读数后 0/7 天判级变化。**这条结果的射程要说窄**：那 7 天是预报接口的**回填段**，两侧在同一时次上都是近分析产品，偏差≈0 有构造性成分，它只说明"历史回填这一步没有可见的跨链路口径差"；**真正跨分布的是 lead 1–16 天的预报段**，而 `FAR_LEAD_DAYS=8` 只压 lead≥8，lead 1–7 的 def30／rain30 窗口照样进判级与文案（`freezeClock` 定灌水日、`nextCooling` 取降温日、`ctx.forecast7` 带归因原文进 LLM），这一段**今天没有任何测量值**——要测需要历史预报（multi-ensemble / previous-runs）在 2022-08 与 2021-12 两个窗口重放"当初预报"，出 lead 1–7 的等级翻转率，列为试点前的下一件事，不做措辞替换。该脚本一次跑一次数、不进闸门，读数随运行日移动。
- **格点提前量与高程（评审 A-R12⑦、A-R13③）**：`tools/grid_sensitivity.py` 现在逐格点打印热害首个重级日、峰值日与提前量，并按**实际落点去重**——旧偏移 0.05° 小于 ERA5-Land 的约 0.1° 网格间距，四个请求点里有两个落到同一格点，"四个相邻格点"是假陈述；现已把步长改为 0.10°（≈11km，真正跨格）并断言去重后 ≥3 个不同格点，不足即退出 1。**此前写在材料里的"3、4、2、3 天（极差 2 天）""46.7%""干旱 59/122""极差 10 天"都来自含重复序列的旧 0.05° 集合，已作废**；2026-10-14 用 0.10° 重跑（四个互不相同的实际格点 32.5835,111.3764／32.7241,111.4286／32.5835,111.4860／32.5132,111.3504，高程 236／348／255／448 m）：逐日 worst 不一致 **54/122＝44.3%**，分风险不一致 **热害 25/122、干旱 61/122、低温 0、冻害 0**，高级别（重）日数极差 **8 天（13–21）**，「提前 N 天」为 **3、2、2、3（极差 1 天）**。另注：`lead_days = 峰值日 − 首个重级日`，格点间提前量差既可能来自预警能力，也可能只是峰值日在各自序列里挪了一天，所以现在把首个重级日（08-04／08-05／08-05／08-04）与峰值日（08-07）一并打印出来——本次四个格点的峰值日相同，极差 1 天全部来自**首个重级日**那一侧。
- **干旱"首日 2022-06-01"是窗口边界，不是提前量证据（评审 A-R12①）**：同一冻结序列上 2022 年最早带干旱等级日是 **03-01**（休眠期轻级），且 **05-28 起连续带级**一路接进报告窗口——`summarize` 在 `windowed()` 之后才找首日，所以这个数天然等于窗口首日。头条里的**时效主张只用热害**（首个重级 08-04、提前 3 天）；干旱首日只读作"该区间第一天就有提示"，不许读成"引擎提前发现"。`--check` 把这个数锁成回归断言，意味着将来更正它时会先被闸门拦下——这是有意的：更正必须是一次显式改数并同步全部载体，而不是让口径悄悄漂。
- **闸门能力的上限要说清（评审 A-R12⑨）**：42 条变异全部来自本项目自己踩过的分叉与往闸门自己身上打的注入，**没有一条来自外生 oracle**（第三方干旱指数实现、官方灾情日报、独立再分析对比）——闸门覆盖面等于"作者想到过的错误集合"，这是它的天花板，不是它通过时该被读成的证据强度。对拍同理：它证明两套实现逐日等价，不证明判级符合农学真值（见本节末"仍未证明的"）。
**仍未证明的**：def30 的绝对农学含义（需田间水分观测，见 docs/03 §3 记录项⑤与 §6）、与本地灾情的逐次对表（docs/03 §6）、以及"用户据此少损失多少"。本节只把分级从"说不清"提升到"可复算、可判失败"。

**冻结输入 ≠ 今天的再分析（`tools/online_drift.py`，2026-10-14 实测；评审 A-Q10 指出"只挑一个对自己有利的贴边点"不算披露，这里给逐变量计数）**：同一坐标、同一区间（含 35 天 warm-up，共 157 天）逐变量比对，**tmax 28 天不同、tmin 99 天不同、降水 23 天不同、ET0 106 天不同**（最大偏差：tmax 0.5℃、tmin 0.9℃、pr 2.2mm、ET0 0.08mm/日）。对结论的影响分两侧算，不合并成一句"漂移很小"：
- **热害侧结论不变，但被引用的数字变了**：冻结与现取都算出"重"13 天、提前峰值 3 天、首日 08-04；然而 08-04 的最高温是 冻结 39.2℃ / 现取 39.3℃（距 39℃ 重级线 +0.20℃ vs +0.30℃）——材料里凡引单个温度值都必须带输入版本，只写"39.2℃"是不完整的。
- **干旱侧变一天**：冻结 重1/中55，现取 重0/中56。改档点确实在 08-26 的"中"级佐证线（雨30 29.90 vs 30.20，距 30.0mm 线 −0.10 vs +0.20 → 判级 重 vs 中），但整段输入都在被修订，只是恰好只有这一个点跨过阈值改变了对外数字——**不能把它说成唯一的漂移来源**。

口径因此写死：头条数字一律标注输入版本与拉取时间（fixture meta 的 `pulled_at_utc`），并给出 `python tools/online_drift.py` 让第三方自己重算差异；而"0.1–0.2mm 就能改档"这一事实本身就是**格点 30 天累计降水不足以单独支撑『重』级判定**的证据，也是 docs/03 记录项⑤（手捏墒情＋灌水日期）必须做的原因。

## 7. 模型与工具使用

### 7.1 确定性风险引擎（核心）
- 实现：`phenology.js`（物候表、四类风险判级、蒸散阈值与封顶）+ `app.js assess()`（前端逐日计算，含 30 天回看窗口与 ET0 完整性判定）；`tools/backtest.py` 提供同规则 Python 独立实现（四类风险全覆盖）用于回测与基线核算。
- 输入：逐日 tmax/tmin/precipitation/ET0（含前 30 天回看窗口）。
- 输出：逐日四类风险等级（无/关注/轻/中/重）与触发依据文本；**等级必须改变行动**——每条建议块随等级附上执行时效（重＝24–48 小时内完成并留痕＋通知农技员；中＝本周内完成；轻＝择机处理、以复查为主），否则"抬高一级"只是把看板换成红色（评审 C-Q1 的指正）；**"无"三态已区分**：今日未触发／该期不适用／判断不了（回看不满 30 天、窗口含缺测、ET0 缺测、休眠期降水口径沉默），且看板、导出报告、CSV 的"干旱说明"列与规则问答四处同规则、措辞为大白话（评审 C-Q6）；
- 特点：全部阈值显式写在代码中、可审计、可回测，两侧等价性被脚本强制。

### 7.2 DeepSeek 大模型解释层（可选接入）
- 接入方式（**两条路径要分清，别把"谁付钱"读串**，评审 B-R8⑦）：对外访客一律用**自己的** DeepSeek API Key（仅存 localStorage，不经任何服务器；页面另有"清除本机 Key／清除本机记录"两个按钮，烟测真的点它们并断言条目被删），本项目没有代付通道；**只有试点那两户**用项目方为试点单独建的一把 Key，用量计入 docs/03 §2 的 ≤100 元预算。前端直连 `api.deepseek.com/chat/completions`。
- 系统提示词约束：只用给定数据上下文与公开农技规则回答；给出可执行动作；必须引用数据日期；**风险等级与数值只能原样引用上下文，不得自行判定等级或预测新数值**；数据不足时明说并建议咨询当地农技部门。
- 上下文含当日与**未来 7 天**逐日数据及引擎等级（早前只给历史 7 天，问"接下来几天"时模型无据可依）。
- 技术侧约束（不只靠提示词）：①等级一律由规则引擎计算并渲染看板，LLM 文本不参与计算；②LLM 返回文本与用户提问回显一律 HTML 转义后渲染（杜绝注入）；③回答尾部固定"风险等级请以页面看板为准，本回答仅为解释；不构成灾害预警"。
- **已补上的缺口（评审 C-Q10）**：`buildContext()` 现在把**建议库的可执行条目全文与执行时效**一并送进上下文（`actions` 字段，含因灌溉条件被排除的条目），模型不必再凭记忆编"灌多少、灌几次、用什么药"；回答返回后由 `llmCheck()` 做事后核对——文本里出现看板没有的"重/中/轻级"就点名；数字按单位分两套白名单——℃/mm 只认看板、预报与阈值字段（凭空的新温度、新雨量必须被抓），其余单位（cm/天/次/升/%/倍/公斤）额外放行本工具自己印出去的建议串与时效串里的数字，否则模型原样引用"覆盖 10cm""3–5 天"反被判越权（评审 A-R8⑥：口径此前是反的）。本轮再补两处（评审 A-R9③④）：上下文的 `today.risks` 除等级外**带上触发依据原文**，白名单从中取数——否则模型原样引用"连续 8 天…44.0 mm"仍被判凭空；测量类单位（℃/度/°C/mm/毫米）**只认原值与一位小数**，不许四舍五入到整数，否则 45.6℃ 会靠阈值 45.9℃ 蒙过去；单位表补全中文写法（毫米、度、小时、日、克、吨等），"换个写法就绕过"不再是漏报面。出现越权项就在答案后追加【自动核对不过】并逐条列出。这是**标注而非拦截**：模型仍可能给出上下文之内但不合适的建议，所以"以看板为准"与免责句保留。烟测用两个构造答案验证这条核对会失败（合规答案 0 项、越权答案 ≥2 项）。本轮再补两条，因为核对原本只管"数字与等级词"，管不到**动作**与**数字的来路**：①**越权动作核对**——门控清单（`gate`）里的动作关键词（熏烟／覆膜／喷施／保水剂／灌透水／疏除…）出现在回答里、而全篇没有任何"确认／咨询／农技员／主管部门"措辞时点名列出，此前模型答"今晚就熏烟防霜"不含数字也不含新等级，`llmCheck` 零命中（评审 C-R12②）；②**日期串不再进白名单**——`addStrings` 原来遍历整个上下文，十几个 ISO 日期把 1–31 与年份全量放进了非计量单位白名单，凭空编"每株灌 2026 升"这类数字大概率抓不到（评审 C-R12⑤），现在只放行本工具自己印出去的建议串、依据串、时效串与物候名里的数字；串里内嵌的 ISO 日期（时效钟会写"下次降温在 2026-12-09"）先被剥掉再取数字，日期本身的"几号/几月"另存一个小集合，**只允许出现在 X 日／X 月 上**——系统提示要求模型必须引用数据日期，全剥会把合规回答"12 月 5 日的判级为……"误判成越权（评审 A-R13⑤③）。越权动作核对同样改了判定单元：原来是全篇一次性开关（一个 hedge 词解除全部关键词，而 `CONFIRM_TAG`＝"【需当地确认后才可执行】"、`gate.说明` 与 `rule` 自己就带"咨询农技员"，模型越照提示引用越必然 no-op），现在**按句判**——含门控关键词的那一句里必须有"确认/咨询/农技/主管部门/不适用"，且否定式（不必/不用/无需/不要…）不算 hedge。"重级先现场核实"那句限定词（`adviceFor().verify`）此前只到看板、导出、问答三处，`buildContext()` 的 actions 条目里没有它，模型照样能输出"24–48 小时内浇透"（评审 A-R13⑥），现已补进第四出口。烟测对这几条各做正反样本（越权样本、否定式样本、合规日期引用样本），并由 M41（取消动作核对）、M42（让串内日期数字重新混进白名单）、M44（把用量白名单退回单一 misc）钉住——M44 是分桶机制自己的守卫：没有它，"时效串的 4/12 与 verify 串的 9 重新变成合法用量"就没人拦。
- **覆盖范围要说明白（评审 C-Q9）**：建议库只实现《湖北柑橘抗高温干旱及灾后恢复技术措施》的"灾中应对"部分；"灾后恢复"章节（旱后修剪与施肥时序、日灼果处理、高温干旱后红蜘蛛等次生病虫）**本轮未入库**——该文件公网只有内部镜像、取不到可逐字引用的文本，我们不凭记忆补写农事条目，已列为 docs/03 §6 试点核对清单第一位。
- **物候表的适用域（评审 C-Q1）**：表是纯日历近似，按"丹江口温州蜜柑、滨湖平地"建模，未建模海拔/坡向/砧木/晚熟品种差异；库区 300–500 m 坡地与滨湖的物候可差一旬以上，所以页面②区把当前物候期与其判定区间原样显示、允许用户否掉，未做本地校准前不给不可逆动作。
- 建议来源的措辞：页面与导出报告在每条规则来源后固定标注"（本项目按公开技术文件自行整理的规则摘录，与发文单位无关联，未经当地核验）"，避免把省厅文件名读成官方背书（评审 C-Q8）。

### 7.3 建议库的外部性分级（fail-closed 的产品实现）
- 数据层：`ADVICE` 中含环境外部性的动作（熏烟与明火、地膜/覆盖材料残膜、大水漫灌与退水、化学品与叶面肥/速效肥）标 `confirm: true`，共 18/44 条（本轮把膨大期"疏除部分幼果、暂停追肥"也升为需确认——它是**对产量本身不可逆**的动作，此前只有环境外部性与采后取舍两类进了 fail-closed，评审 C-R12③；本轮又为花期/现蕾/幼果低温各补了一条**无需投入品的观察留档动作**，并为晚熟杂柑挂果期补了抢收/覆盖保果条目；这两个数由 `tools/advice_counts.mjs` 现算并与本句比对）。
- 行为层：这类动作**默认不进入"可执行建议"列表**，而是单列"待当地确认清单（未确认前不作为可执行建议）"；每条待确认项自带**确认开关**（勾选后写入本机 `localStorage.confirmed_actions`，该项才升格为可执行并标注"已经当地确认"；再取消即退回）。看板与问答同一规则；导出的报告里不放开关而放**签字栏（确认人／日期）**——因为确认状态只存在本机、跨设备不同步，农技员在自己手机上勾过的选项不会出现在农户设备上。
- **园块条件记录有有效期（评审 A-R9⑩）**：挂果与否门控的是"抢收/覆膜保果"这类**不可逆**动作，所以不能建立在陈旧输入上——`fruit_cond` 超过 90 天（约一个物候周期）即按"未记录"处理，提示条写明"已超过一个物候周期，按未记录处理"；12 月点的"仍挂果"到 6 月不会继续让工具建议抢收。灌溉条件不设过期（设施跨年稳定），但同样只在用户改选或按下清除按钮时变。
- **"撤回方式"要连后门一起堵（评审 A-R9⑤）**：`clearLocalRecords()` 除删除园块条件与确认清单外，还抹掉本次会话里输入过的"确认人／依据"缓存——否则清完之后不重新署名就能再勾一次确认，撤回只做半截。回显文案分开说明"删了什么、没删什么"（Key 与记录是两个按钮、两件事）。
- 机制保障（本轮补三件，评审 A-R9⑦⑧⑨）：①事件委托从初始化段抽成 `wireDelegates()`，烟测把 `change`/`input` **事件真的派发进去**（此前只直接调处理函数，删掉 `addEventListener` 那行照样全绿，而真机复选框全废）；②烟测拿 `index.html` 与 `app.js` 做 id 交叉核对，DOM 桩不会替缺失的元素"自动造出来"；③降水口径的分级从判定链里抽成 `backtest.rain_track()` 单一实现，材料闸门的休眠期常驻率改为调用它——原来那里手抄了五个阈值字面量，等于第四份规则副本，两侧同步改阈值时它会算出错的"权威值"却全绿。同一轮把 `preflight()` 的语法校验扩展到 Python（`ast.parse`），因为 44 条变异里有 11 条的注入点在 .py 里。
- 机制保障：`tools/smoke_app.mjs` 用关键词（熏烟/覆膜/地膜/磷酸二氢钾/保水剂/叶面肥/速效肥/喷药/灌透水/冻前灌水/追施）做**语义断言**——凡命中关键词必须挂 confirm、未确认项必须落在待确认区，且实测"勾选→升格→取消"全链路；拆掉任一标记都会被闸门拦下（`mutation_test.py` M12/M13）。**导出报告正文本轮才被真正执行过**：`exportReport()` 里原本有一处引用了不在作用域的 `items`，凡是灌溉条件"未记录"（即新用户默认状态）的园块点导出就会抛 ReferenceError——因为三条出口此前只有看板与问答被烟测跑过。现把正文拆成 `reportHtml(t)` 供烟测直接断言（含不适用分段、时效钟、记录值三处），并加 M27（把正文掏空即拦下）钉住。
- **田间可执行性（评审 C-Q6/C-Q7）**：动作还能带 `irr: true`（需灌溉条件）或 `fruit: true`（需树上仍挂果）标记。页面①区有"本园块灌溉条件"与"本园块挂果情况"两个选择（有/无/未记录，按园块分别存本机 localStorage）：选"无灌溉"时"浇透根系分布层"一类动作被移出可执行段、选"已采收完"时抢收与覆膜保果条目被移出，两者都单列"按本园块记录不适用的动作"并写明不适用的原因；选"未记录"时保留但加注"请先确认能否执行"。看板、导出报告、规则问答与进 LLM 的 actions 四条出口共用同一个分段函数（`adviceFor`/`adviceLines`），不允许各算各的。**挂果与否之所以是输入而不是注释**：本表按蜜柑 10 月集中采收建模，而晚熟杂柑 12–1 月仍挂果——同一格点、同一天，"要不要抢收"取决于园块，工具不能替用户假设（此前它写的只是一句带"若"字的假设，把判断推回给用户）。
- **不再出现"红色等级＋空动作清单"（评审 C-Q6）**：花期/现蕾/幼果低温的"重/中"级原先三条动作全是待确认项，页面只能显示"暂无可自动执行的动作"；现在每个这类风险都至少有一条无需投入品、无需审批的观察动作（逐株记录最低温与花量/幼果受害、拍照留档），用户拿到等级当天就能做且能核对。
- **连日同级不重复发同一条紧急指令（评审 A-R12②）**：`adviceFor()` 现在按 `window.__recent` 回看同一风险的**连续**天数，第 2 天起在时效行后附"本等级已连续 N 天：先核查上一条是否已执行、记录墒情与树势变化，已执行就转入维持动作；只有仍未执行才继续按原时效处理"。这条是被自家标准逼出来的——docs/02 §4 写"等级必须改变行动，否则抬高一级只是换颜色"，而留出段 2025 年有**连续 36 天**的花期"重"级，第 20 天照印"24–48 小时内完成、同时通知农技员"就是狼来了。计数只认同日相邻的连续日（缺一天即重新起算，烟测专门测断日），并同串进看板、导出报告、规则问答与 LLM 的 actions；M43（把去重拼接拆掉）由烟测拦下。注意这与 `dry_streak`（无有效降水的连日数）是两套计数：一个数天气，一个数等级本身。
- **冻害时效不再一刀切 24–48 小时，并且带一把钟（评审 C-Q3/C-Q7）**：`RISK_TIMING.freeze` 覆写——物理防护（涂白/培土/覆盖）立即做，**冻前灌透水要求距降温 3–5 天**。光有这句话农户仍然不知道降温在哪一天，所以 `freezeClock()` 直接从引擎自己对未来预报日的判级结果里取"下一个触发冻害的日"（不另设温度阈值，避免两套口径），钟只用 **lead < 8 天**（`FAR_LEAD_DAYS`）的预报日：8 天及以上的那批已被 `capFarForecast` 压成"关注"并写明"不构成动作依据"，同一条读数不能一边被判不可用于行动、一边被钟拿来定灌水日（评审 A-R8⑤，边界与 `capFarForecast` 逐字对齐，烟测专门测 lead=8）。拼进时效行的分支共 7 条：预报序列取不到→明说"算不出降温日，按当地霜期与官方预警防护"，**不把缺数据说成缺风险**（评审 C-R8③）；8 天内无降温日但更远有→给示意日并声明"已被封顶、不作灌水依据"；8 天内确无降温日→照实说；"轻"级→只报降温日、不下灌水指令（评审 C-R8④）；>5 天→给"安排在 D−5～D−3 之间"；3–5 天→"已在窗口内，今明两天做"；<3 天→"不要临冻灌透（根区结冰风险），改用覆盖/涂白/培土"。看板、导出报告、规则问答与 LLM actions 同串。**钟对记录为"无灌溉"的园块不下灌水指令**——`>5 天`与`3–5 天`两条分支改述为覆盖/培土/涂白，因为建议库里的灌水条目会被园块条件移进"不适用"，而钟原本不读这个条件，同一块地里一边说"要灌透水就今明两天做"、一边说"冻前灌透水不适用"（评审 A-R12①）。前置钟的措辞按**被指向那一天自己的等级**取：今日未出冻害级时不再硬编码"中"，否则"信号更弱"的屏反而拿到比真实"轻"级读数更强的指令（轻级分支明写"不据此安排灌透水"）。无等级屏的前置钟同串进导出报告与规则问答（评审 A-R12①：此前只有看板与问答有，导出件里没有，而本节写的是"四条出口同串"）。烟测对这 7 条分支逐一断言，M26 取消拼接、M30 把缺预报谎报成无降温均由烟测拦下。

- **条件过滤的三个新缺口本轮补上（评审 C-R8①④⑥）**：①`irr`/`fruit` 标记可由条目**显式写 false**——关键词表会把"无水源时拉水浇根"这类专为无水园写的动作误判成需灌溉条目，再被无水块过滤器标成"不适用"，等于工具把唯一做得到的救命动作删掉；②挂果门控覆盖到采收期那条"抢收已熟果"（此前只打了休眠期那条，记录为"已采收完"时采收期仍照发抢收）；③挂果情况"未记录"时，抢收与覆膜保果这类**不可逆**动作不进可执行段，而是进"先记录再决定"段并带独立标记——默认乐观假设等于替农户决定，而看板、导出、问答、LLM 四条出口共用同一判定。
- **数据不足时不许编动作（评审 C-R8⑩）**：规则问答此前在旱情未判级时按"中"级取库，同页一处写"今天判断不了旱情"、另一处却输出"立即灌溉补墒、浇透根系分布层"。现在未判级就明说不给灌水动作及原因。
- **导出的"点得动"这一层本轮才补上（评审 A-R8⑧⑨）**：材料写过"撤回方式=可清除本机记录"，但页面两个清除按钮在 app.js 里没有任何 onclick 绑定，点开什么都不发生；烟测当时只测正文函数 `reportHtml`，用户真正点的 `exportReport()` 与 `downloadFile()` 仍零执行。现在烟测给全桩（可枚举并删除的 localStorage、可 click 的 a、URL/Blob），真的调用 `exportReport()` 断言下载文件名带日期、真的调用 `wireLocalControls()` 后点两个按钮断言 Key 与园块条件/确认清单确实被删；M32 把清除函数改成空操作即被拦下。
- 诚实边界：本工具无推送通道，"不推送"在产品上等于"不作为可执行建议呈现"；确认记录仅存本机、跨设备不同步，因此它不能被当作合规凭证（凭证是签字件与逐日判级 CSV）。

### 7.4 为什么不是"为了 AI 而 AI"
- 没有大模型时产品依然完整可用（规则引擎 + 规则问答 + 导出报告/CSV）；
- 大模型解决"同一份数据对不同用户的不同表述 + 支持追问"这一具体负担，任务边界明确；
- 评审可复算：回测与基线脚本独立于前端，且已证明两套实现逐日等价、阈值与定标同源。
