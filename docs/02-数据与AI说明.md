**失败模式与可观测性**（唯一外部依赖，故显式处理）：每次请求 12 秒超时 + 一次重试；返回前做契约校验（`daily.time` 与三个变量数组必须存在且等长，字段缺失/长度不齐即显式报错，不让 `undefined` 静默变成等级）；历史序列与预报序列**分别降级**——archive 挂了就仅显示预报并提示"干旱暂不判级"，预报挂了就仅显示再分析，两侧都挂才报错并给出各自原因。

**已知局限（诚实声明）**：
1. ERA5-Land 为格点再分析，与具体果园实测存在偏差——"园块"实为用户坐标映射到最近格点的乡镇尺度背景场，非单园实测（请求坐标 32.60,111.42 → 实际格点 32.5835,111.3764，海拔 236 m）。**我们尚无同站偏差统计**：竹山站 44.6℃ 与格点 40.9℃ 是不同站、不同日的叙事性对照，不构成该格点的系统偏差估计；格点 vs 丹江口站逐日偏差统计列入试点前补做（Mean Bias + 极端日分位，脚本随材料开源）。正式版将接入省气象局授权的乡镇级实况/预报数据（湖北已有气象数据授权运营机制）；
2. 物候表为库区常规年景近似日历区间，未建模年际波动与品种差异（暖冬年花期可提前 7–10 天）；区间已无缝覆盖全年且**由脚本逐日核算 2016–2028 每一天都显式命中区间、不依赖兜底分支**（此前闰年 2/29 会静默落入兜底，已修）；中期计划改积温模型；阈值属文献推定，待 2027 花期试点校准；
3. 干旱指标采用"连续无有效降水日(<1mm) + 30 天日历窗口累计降水"双指标，**休眠期不出干旱等级**：经十年基线核算（`tools/baseline_stats.py`，3653 天），若休眠期照判，**89.8% 的越冬天数会带干旱等级、其中 37.5% 为"重"级**——本区 12–2 月的气候常态即可触发阈值，常驻等级≈纯噪声（狼来了效应）。这是噪声控制而非能力撤回：墒情信号改由越冬冻害建议中的"捏土验墒（10cm 土层手捏成团不散则缓灌或不灌）"可执行动作承载。另外：回看窗口不满 30 天一律不判级（缺测日会使累计降水系统性偏低、等级虚高，原先"照判+文字标注"的做法已废弃）；暴雨后 30 天窗口内雨量计入累计、干旱自然退出（保守取舍，未做土壤水分订正）；ET0 口径的可行性见第 7 节；
4. 阈值为文献通用值，试点期将用合作社地块反馈校准；
5. **预报路径零回测**：实时运行中当日等级依赖 ECMWF 预报（archive 滞后 2–5 天，代码取至 now−6d 并用预报 past_days=6 回填），"提前 3 天"是描述性回测指标而非预报技巧。预报回测的**验收口径**（承诺条款）：①序列选用 Open-Meteo 历史预报存档的 ECMWF 单模型，与线上 best_match 混合序列的差异单独声明；②判定规则=逐日等级差 ≤1 档记可用、≥2 档记误报，按预报时效（lead 1–3/4–7/8–16 天）分箱统计；③90 天试点极端过程期望 ≤2 次，只作记录与积累，技巧评估依托历史存档年度样本。8 天外预报等级已封顶"关注"并以"模式值"口径展示。

## 2. 可复算性：三条命令，全部离线可跑

评审不需要当场联网、也不必区分"差异来自引擎还是数据"——输入序列已冻结进仓库：

```bash
python tools/backtest.py --fixture tools/fixtures/liangshuihe_2016_2025.json \
       --start 2022-06-01 --end 2022-09-30 --check   # 头条数字回归闸门（联网亦可：python tools/backtest.py）
python tools/parity_check.py                         # JS↔Python 逐日对拍 + 23 组边界用例 + 物候表无洞
python tools/baseline_stats.py                       # 十年提示负担基线、休眠期常驻率、ET0 口径试验
```

`parity_check.py` 是"任一侧规则改动须同步对拍"这句承诺的**执行机制**：真实序列四个窗口（热害季/越冬期/春夏物候边界密集区/秋汛至采收）共 442 天逐日比较四类风险等级与物候判定；另造合成序列把阈值边界（rain30 的 15/30/45mm、连旱 8/15/25 天、连续高温 3/5 天、单日 33/35/37/39℃、跨物候边界跳档、断链清零、窗口不满 30 天、闰日）逐一打到，期望值按规则文本单独写死（不取自任何一侧实现）。任一天不一致或用例不命中即退出码非零、禁止提交。当前状态：**442 天逐日等价、23 组边界用例全通过、JS 与 Python 物候表逐条一致且 2016–2028 无未覆盖日期**。

## 3. 回测结果（真实数据，2022-06-01~09-30，凉水河格点）

```
≥35℃ 日数: 30
热害『重』级日数: 13
极端最高温: 40.9℃（2022-08-07）
首个『重』级提示: 2022-08-04（39.2℃，当日连续 3 天 ≥35℃）
首个『重』级触发方式: 单日 ≥39℃
提示相对峰值提前: 3 天
『重』级中由连续日数升级产生（当日 <39℃）: 3 天，最早 2022-08-10
干旱：首个『轻』级以上提示 2022-08-05；『重』0 天、『中』3 天；最长连旱 12 天
```

**时效归因（重要，不抢功）**：把提示时效记在"连续日数升级"机制上是错的——2022 序列中首个"重"级由**单日 ≥39℃ 阈值**触发（08-04 达 39.2℃，早于 08-07 的 40.9℃ 峰值 3 天）；连续日数升级在该过程另贡献 3 天"重"级，但最早出现在 08-10（峰值之后）。因此"提前 3 天"的证据支持的是**分级阈值链条**（当日 39.2℃ 已足以判"重"并给出防护窗口），升级机制的价值在于长过程的中重级持续覆盖（13 天），二者不混记。
**结论**：工具在 2022 年极端事件中可提前 3 天给出最高级热害提示，且整个高温过程持续输出中重级提示 13 天，覆盖灾前防护窗口。

## 4. 提示负担基线（2016–2025，各级出现日数／年，中位数与范围）

回答"轻/关注级会不会把人训练成忽略提示"必须有的底数（`tools/baseline_stats.py` 可复算）：

| 风险 | 重 | 中 | 轻 | 关注 |
|---|---|---|---|---|
| 高温热害 | 0（0–13） | 2（0–9） | 8（2–11） | 22（8–32） |
| 干旱（休眠期不判级） | 8（1–17） | 32（10–63） | 50（28–69） | — |
| 花期/幼果低温 | 0（0–1） | 2（0–3） | 4（2–8） | 12（7–18） |
| 越冬冻害 | 0（0–9） | 2（0–11） | 6（0–15） | — |

读法：正常年景一个园块每年约收到 22 个"关注"与 8 个"轻"级热害日提示、50 个"轻"级干旱日提示，而"重"级热害中位为 0 天——**高级别信号确实稀有**（这正是把越冬期干旱常驻等级去掉的理由：那会把"重"级从稀有信号变成常态噪声）。试点指标据此增设**提示负担**项：每用户每周收到的"轻+"级提示条数上限与实际查阅条数，作为与采纳率并列的"是否狼来了"监测（见 `docs/03` §3）。

## 5. ET0 水分亏缺口径试验（为什么首发版不上）

Open-Meteo 的 `et0_fao_evapotranspiration`（FAO 参考蒸散，mm/日）在 **Archive 与 Forecast 两端点均有日值**，本项目已实测可取（注：土壤水分变量仅有小时值、需自行日聚合；早前文档写的 `et0_reference_evapotranspiration` 变量名在两端点实测均返回 invalid，已更正）。以 def30 = 近 30 天 ET0 − 近 30 天降水构造"水分盈亏"口径，按物候期分布为：

| 物候期 | n | p50 | p75 | p90 | p95 | max |
|---|---|---|---|---|---|---|
| 休眠 | 963 | 22.5 | 33.6 | 40.3 | 43.5 | 56.2 |
| 萌芽/现蕾 | 400 | 31.1 | 43.0 | 56.8 | 60.5 | 85.5 |
| 开花 | 310 | 39.9 | 55.3 | 86.0 | 93.3 | 107.2 |
| 幼果 | 410 | 60.5 | 83.5 | 102.3 | 106.1 | 145.9 |
| 膨大 | 920 | 16.1 | 54.1 | 87.4 | 102.3 | 138.3 |
| 成熟采收 | 650 | −6.7 | 31.4 | 55.5 | 71.5 | 122.8 |

**试验结论（否定自己的捷径方案）**：把 def30 作为额外触发条件直接 OR 并进现有阈值，膨大期"重"级年日数中位将从 **0 天（0–5）升到 38 天**（def30≥40mm 时触发率 34.7% 的天数）——"重"级失去区分力。原因是 def30 跨物候期不平移（休眠期 p50 已 22.5mm，膨大期 p50 仅 16.1mm，两季蒸散背景差异巨大）。因此 ET0 口径的正确用法是**按物候期分别定距平分位阈值**，且必须与田间实测水分、农户响应联校才能定标；首发版不凭推测上线，列入 `docs/03` 试点校准任务（候选阈值：休眠 p90≈40mm、膨大 p90≈87mm、开花 p90≈86mm）。

## 7. 模型与工具使用

### 7.1 确定性风险引擎（核心）
- 实现：`phenology.js`（规则表与四类风险判级）+ `app.js assess()`（前端逐日计算）；`tools/backtest.py` 提供同规则 Python 独立实现（四类全覆盖）用于回测与基线核算。
- 输入：逐日 tmax/tmin/precipitation（含前 30 天回看窗口）。
- 输出：逐日四类风险的等级（无/关注/轻/中/重）与触发依据文本（如"最高温 40.9℃，已连续 6 天 ≥35℃；当前果实膨大期，日灼与落果风险高"）。
- 特点：全部阈值显式写在代码中，可审计、可复算、可回测，且两侧等价性被脚本强制。

### 7.2 DeepSeek 大模型解释层（可选接入）
- 接入方式：用户在本机填入自己的 DeepSeek API Key（仅存浏览器 localStorage，不经过任何服务器），前端直连 `api.deepseek.com/chat/completions`（OpenAI 兼容协议）。
- 系统提示词约束：只使用给定数据上下文与公开农技规则回答；给出可执行动作；必须引用数据日期；**风险等级与数值只能原样引用上下文，不得自行判定等级或预测新数值**；数据不足时明确说明并建议咨询当地农技部门。
- 上下文含当日与**未来 7 天**逐日数据及引擎等级（早前只给历史 7 天，果农问"接下来几天"时模型无据可依，已修）；未填 Key 时自动降级为内置规则问答，功能不缺失。
- **技术侧的三道约束（不只靠提示词）**：①风险等级一律由规则引擎计算并渲染在看板，LLM 文本不参与等级计算；②LLM 返回文本经 HTML 转义后渲染，杜绝注入（用户提问回显同样转义）；③LLM 回答尾部统一附加"风险等级请以页面看板为准，本回答仅为解释；不构成灾害预警"。
- **仍存在的缺口（不捂）**：没有对 LLM 文本做"等级词/数值与引擎一致性"的自动后校验——若模型在文字里自行写了一个更高的等级，目前靠声明引导用户回看看板，而非程序拦截。列入规模化前任务（需轻量后校验：抽取文本中的等级词与 `today.risks` 比对，不符则拒渲并回退规则答案）。
- **失败模式已可见**：网络/跨域被拦截或 API 报错时，明确提示是哪种失败并说明"规模化需服务端代理"，再回退规则问答。

### 7.3 为什么不是"为了 AI 而 AI"
- 没有大模型时，产品依然完整可用（规则引擎 + 规则问答 + 导出报告/CSV）；
- 大模型解决的是"同一份数据对不同用户不同表述 + 支持追问"的具体负担，有明确任务边界；
- 评审可复算：回测与基线脚本独立于前端，用同一套阈值验证 2022 年事件的提示时效，且已证明两套实现逐日等价。
